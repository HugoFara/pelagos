About this map

The original 51 repo nodes and their aggregate stats (stargazers, forks, open issues, watchers, contributors) come from data/processed/repo_aggregates.json — real hasTotalForks/hasTotalOpenIssues/hasTotalWatchers/hasTotalContributor triples for the top-starred cohort. Stargazers are capped at exactly 10000 in this dump, so node size is driven by fork count instead (see NOTES.md). Five differently-colored repo-repo edge lenses over the cohort, all actually pulling their connected repos together (not just drawn): __DEPENDENCY_EDGE_COUNT__ directed dependency edges (arrowed, on by default, toggleable in the legend — the one edge type here that isn't a shared-person proxy, A really does depend on B): real usedPackage triples resolved from PyPI package name back to the GitHub repo that publishes it (scripts/09_resolve_packages.py), which is how the cohort grew past the original 51 — every newly-added node either publishes a package another repo in this dataset actually imports, or is one of the real academic repos doing that importing (a top-100 slice by distinct-dependency count, out of ~21,100 candidates — see scripts/10_fetch_new_repo_stats.py). Hover an arrow to see the actual package name(s) behind it, and see scripts/15_trophic_levels.py for how this tier alone also drives the graph's vertical axis (Phase 12). __SEMANTIC_EDGE_COUNT__ semantic edges from repo_semantic_edges_pruned.json (on by default, toggleable in the legend) — two repos sharing real GitHub topic tags (min 2 shared, top-4 pruned; hover an edge to see the actual shared tags), a first, crude cut at a subject-matter relationship rather than a dependency or audience one; see scripts/16_topic_circular_embedding.py for how the same topic data also drives the graph's circular axis, independent of whether this tier's lines are toggled on. __EDGE_COUNT__ shared-stargazer edges from repo_shared_edges_pruned.json (the full overlap across the original 51 repos, pruned to each node's top-4 strongest) and __CONTRIB_EDGE_COUNT__ shared-contributor edges from repo_shared_contributor_edges_pruned.json (real overlapping hasContributor sets, min 2 shared, top-4 pruned) are not a legend toggle (Phase 12) — both are "linked via a shared person" proxies, always contributing a gentle attraction force but only ever drawn when they touch the repo currently hovered or selected, hover an edge once shown to see who the shared contributors are. __ISSUE_AUTHOR_EDGE_COUNT__ shared issue-poster edges from repo_shared_issue_author_edges_pruned.json (Phase 19) join that same not-a-legend-toggle family — real overlapping hasIssueAuthor sets over a capped per-repo issue sample (scripts/23_shared_issue_authors.py, since the dump has 2.6M issue triples total; only 74 of this cohort's repos have any issue data at all in this dump), min 2 shared, top-4 pruned; hover an edge once shown to see who the shared issue posters are. __EXPANDABLE_COUNT__ of the original 51 repos (dashed ring) also have a real, capped individual-level neighbor sample — issues, stargazers, watchers, forks, contributor references — from repo_expansions.json; click one to expand or collapse it in place. Those individual-level node types are hidden by default (only the repo-repo layer shows out of the box) — check a type in the legend to reveal it across all expanded repos. The predicate table at left is an exact tally over all 82,078,636 triples (grep -oP + sort | uniq -c over the full file) — 53 distinct predicates total, top 10 shown. All URIs, labels, and counts displayed are real values from the dataset, not simulated.
